## 1. نبذة عن المشروع

**NexusAsset Cloud** منصة مؤسسية تهدف إلى توحيد قدرات اكتشاف الأصول
التقنية وإدارتها مع العمليات المؤسسية والتجارية ضمن نظام واحد. تعتمد
المنصة على التكامل مع **Lansweeper** للاستفادة من بيانات اكتشاف الأصول،
ثم توسيع استخدامها لتغطية احتياجات الإدارة والحوكمة والتشغيل.

تجمع المنصة المجالات والقدرات التالية:

  -----------------------------------------------------------------------
  المجال                              الوصف
  ----------------------------------- -----------------------------------
  **CMDB**                            إدارة قاعدة بيانات عناصر التكوين
                                      والعلاقات بينها.

  **ITAM**                            إدارة الأصول التقنية ودورة حياتها.

  **الحوكمة**                         تطبيق السياسات والضوابط المؤسسية.

  **التدقيق**                         تسجيل الأنشطة والأحداث وتوفير أدلة
                                      المراجعة.

  **الفوترة**                         دعم العمليات التجارية والفوترة.

  **تعدد المؤسسات والعملاء**          عزل بيانات كل مستأجر ضمن بنية
                                      متعددة المستأجرين.

  **واجهة الويب وBFF**                تقديم واجهة ويب وطبقة وسيطة للاتصال
                                      بالخدمات الخلفية.

  **واجهات الأجهزة المحمولة**         توفير واجهات API لاستهلاك تطبيقات
                                      الهاتف.

  **قابلية الرصد**                    متابعة حالة الخدمات والأداء
                                      والأحداث التشغيلية.

  **DevOps وCI/CD**                   تنظيم البناء والاختبار والنشر
                                      والتشغيل.
  -----------------------------------------------------------------------

> **طبيعة المستودع:** يمثل هذا المستودع مواصفات تأسيسية وخطة تنفيذ
> مرحلية. لا ينبغي اعتبار وجود مواصفات أو هياكل أولية دليلاً على اكتمال
> جميع وظائف النظام أو جاهزيتها للإنتاج.

## 4. المعمارية العامة للنظام

واجهة الويب عن الخدمات الخلفية، مع استخدام PostgreSQL لتخزين البيانات
وRedis للمهام غير المتزامنة والتخزين المؤقت.

## 5. قواعد Clean Architecture

تعتمد المنصة مبدأ توجيه الاعتماديات إلى الداخل؛ أي أن طبقة المجال لا
تعتمد على تفاصيل أطر العمل أو قواعد البيانات أو خدمات التكامل.

### 5.1 اتجاه الاعتماديات

``` mermaid
flowchart LR
    I["Interfaces<br/>DRF · BFF · UI"]
    A["Application<br/>Use Cases · DTO · Ports"]
    D["Domain<br/>Entities · Rules · Events"]
    INF["Infrastructure<br/>ORM · Lansweeper · Redis · Adapters"]

    I --> A
    A --> D
    INF -.->|تنفيذ المنافذ والعقود| A
```

### 5.2 قواعد معمارية إلزامية

1.  **استقلال طبقة المجال:** يجب ألا تحتوي `Domain` على استيرادات مرتبطة
    بـ Django أو ORM أو أي إطار عمل.
2.  **مصدر موحد لعقد API:** تكون مواصفة OpenAPI 3.1 المرجع الأساسي لعقود
    واجهات API.
3.  **عزل المستأجرين:** يعتمد العزل على `tenant_id` وسياسات PostgreSQL
    Row-Level Security (RLS).
4.  **مزامنة قابلة للاعتماد:** يجب أن تكون مزامنة Lansweeper قابلة
    لإعادة التنفيذ دون تكرار الآثار، وقابلة للرصد، ومتوافقة مع مصفوفة
    ملكية الحقول (Field Ownership Matrix).
5.  **فصل المسؤوليات:** لا يوضع منطق الأعمال داخل واجهات العرض أو طبقات
    التكامل أو تفاصيل البنية التحتية.

## 8. خطة التنفيذ المرحلية

ينفذ المشروع وفق مراحل متتابعة. يجب قراءة تعليمات المشروع العامة أولاً،
ثم تنفيذ كل مرحلة والتحقق من نتائجها قبل الانتقال إلى المرحلة التالية.

### 8.1 نقطة البداية

ابدأ بقراءة:

-   `prompts/README.md`
-   `prompts/00-global-context-and-rules.md`

تحدد هذه الملفات سياق المشروع وقواعد التنفيذ التي يجب الالتزام بها خلال
جميع المراحل.

### 8.2 تسلسل المراحل

``` mermaid
flowchart TD
    S(["البداية"])
    P0["قراءة تعليمات prompts العامة"]
    P1["01 · التأسيس"]
    P2["02 · الخدمات الخلفية"]
    P3["03 · API وOpenAPI"]
    P4["04 · تكامل Lansweeper"]
    P5["05 · الواجهة الأمامية وBFF"]
    P6["06 · تطبيقات الهاتف"]
    P7["07 · الاختبارات وبوابات الجودة"]
    P8["08 · DevOps: Docker وTraefik"]
    P9["09 · CI/CD: Jenkins وAnsible"]
    P10["10 · الأمن"]
    P11["11 · قابلية الرصد"]

    S --> P0 --> P1 --> P2 --> P3 --> P4 --> P5 --> P6
    P6 --> P7 --> P8 --> P9 --> P10 --> P11 --> P12 --> P13 --> G

```

### 8.3 ضوابط تنفيذ المراحل

-   نفّذ كل مرحلة في جلسة عمل مستقلة عند استخدام تعليمات التنفيذ
    المرحلية.
-   راجع مخرجات المرحلة واختبرها قبل الانتقال إلى المرحلة التالية.
-   لا تعتبر CI/CD أو تقوية بيئة الإنتاج جاهزة قبل نجاح التحقق من
    التشغيل المحلي.
-   وثّق القرارات المعمارية المهمة في ADRs.
-   لا تتجاوز بوابات الجودة بحجة اكتمال كتابة الشيفرة.
-   عند فشل أي تحقق، عالج السبب وأعد الاختبار قبل اعتماد المرحلة.

  الفحص الأمني                        تنفيذ فحوصات الأمان المعتمدة.

  البناء والحزم                       التأكد من نجاح Build وPackage.

### قرار القبول

لا يصدر قرار **GO** إلا بعد استكمال الفحوصات المطلوبة وتوثيق نتائجها.
أما وجود إخفاق جوهري أو اختبار غير مكتمل فيستدعي قرار **NO-GO** إلى حين
المعالجة وإعادة التحقق.

## 11. الأمن والحوكمة

تلتزم المساهمات والتغييرات في المشروع بالسياسات والضوابط الموجودة في
`project-meta/`، مع مراعاة المبادئ التالية:

-   الحفاظ على عزل بيانات المستأجرين وعدم السماح بتجاوز حدود الوصول
    بينها.
-   عدم حفظ كلمات المرور أو مفاتيح API أو الشهادات أو الأسرار داخل Git.
-   الالتزام بمعايير التسمية المعتمدة.
-   تطبيق ضوابط الأمن والتحقق من المدخلات والصلاحيات.
-   الاحتفاظ بسجلات التدقيق اللازمة لتتبع الأنشطة.
-   توثيق القرارات والتغييرات المؤثرة في المعمارية.
-   التحقق من الاعتماديات قبل اعتماد البناء أو النشر.

> التفاصيل التنفيذية الملزمة للأمن والحوكمة تُستمد من وثائق
> `project-meta/` و`docs/07-security/`، ولا يحل هذا الملخص محلها.

## 12. المساهمة في المشروع

المستودع مهيأ ليكون أساساً مفتوحاً للتطوير وفق السياسات والترخيص المحددين
في `project-meta/`. قبل إضافة أي تغيير:

1.  راجع وثائق النطاق والمعمارية ذات الصلة.
2.  اقرأ تعليمات التنفيذ العامة في `prompts/`.
3.  التزم بأسماء النطاقات والخدمات والحزم المعتمدة.
4.  حافظ على قواعد Clean Architecture وعزل المستأجرين.
5.  أضف الاختبارات المناسبة للتغيير.
6.  حدّث الوثائق وقرارات ADR عند الحاجة.
7.  لا تعتمد التغيير قبل اجتياز بوابات الجودة ذات الصلة.

## 13. ملاحظات مهمة حول حالة المشروع

-   هذا الملف هو مدخل تعريفي وتنظيمي للمشروع، وليس بديلاً عن المواصفات
    التفصيلية.
-   أسماء الإصدارات والتقنيات الواردة تمثل المستهدف المعماري المحدد في
    مواصفات المشروع.
-   يجب التحقق من حالة التنفيذ الفعلية داخل `platform/` ووثائق المراحل
    قبل وصف أي ميزة بأنها مكتملة.
-   لا تُعد البنية المقترحة دليلاً على إعداد بيئة إنتاج أو تفعيل جميع
    خدماتها.
-   المرجع المعتمد للتراخيص والسياسات هو مجلد `project-meta/`.
